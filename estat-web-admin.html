Estat Web Admin

From a Java launcher to a web app: redesigning Estat Web Admin on the eUI design system

About the project

Estat Web Admin is the tool statisticians use to write scripts, browse data objects and inspect results in Eurostat's MDT environment. The old version ran from a Java launcher.

I redesigned its three core screens, one at a time with a business analyst, using the eUI design system of the European Commission.

(01) Research

Understanding what each screen is for before touching its look

The application had grown around its functionality. Screens worked, but they looked like a different product from the rest of the Commission's web tools, and the way to use them was learned by doing. Rather than start from a blank canvas, I started from the live system. My motivation was to learn how to bring a dense, expert tool into a design system without flattening what experts rely on.

I sat down with the business analyst and went through every screen, one by one: who uses it, what they do there, which parts are daily and which are occasional, and which labels are domain vocabulary I must not rename. The analyst owned the domain, while I owned the question, “What would a first-time user make of this?”

Context, constraints, goal Three screens carry most of the work: Language Interactive (write and run scripts), Objects (find and manage data objects) and Results (read the output). The constraint was the design system: every pattern had to exist in eUI, or be a justified extension of it. The goal was one consistent, learnable product without removing any capability.

What the audit found

ScreenFindingAgreed with the analyst
Language InteractiveCompile, execute and debug are three unlabeled icons. A first-time user has to hover or guess, and the script tab gives no hint that more than one script can be open.Keep all three actions, group them, and make them self-explanatory. Support several open scripts.
ObjectsThe object type is a single letter (D, F, N, R, T) with an icon in a separate column. The owner tree, filters and column picker sit in different corners of the screen.Keep the letters, since users know them. Gather search, filters and actions in one toolbar above the list.
ResultsEvery cell has a border. Nothing signals that columns can be sorted. Obs Decimals, Obs Conf and Obs Status are mostly empty but take the same space as Obs Value.Lighten the table, add sorting, and let users show or hide columns.

(02) Sketching & wireframing

Annotating the old screens as the shared brief

Instead of redrawing low-fidelity wireframes in a vacuum, I annotated screenshots of the existing screens. The annotations became the working document between the analyst, the developers and me. Each note names the eUI component to use (for example the tree list for the owner tree, a dropdown for the Owner and Type filters, an outline dropdown button for Actions and Columns), points at what should be labeled, and flags what is optional so the developers did not build more than the analyst had approved.

Language Interactive

Compile, execute and debug get labels, so they stop being three mystery icons.

Objects

Component names for the tree, the dropdown filters and the Actions and Columns buttons, plus the optional pieces.

Results

Copy and paste called out in the toolbar, so the data can leave the screen.

Moment of conflict On the script editor the toolbar mixed two different jobs: running code (compile, execute, debug) and handling the file (save, print, copy, paste). Annotating it showed that the two sets sat side by side with the same visual weight, so a mis-click on "debug" cost as much as a click on "print".
UX decision Group the toolbar by intent: run actions first, file actions second, and text search (Find next, Replace) as words, not icons, because editing is where people already read labels. Settings and history move to the far right, out of the way.

(03) Design system

Building every screen from eUI instead of drawing new parts

The European Commission publishes eUI as its shared design system, so the rule was simple: look for an eUI component first, and only extend it when the screen truly needs more. For each screen I mapped the old pattern to its eUI counterpart with the analyst, so that nobody had to guess during development.

One rule One main action per screen, in the primary blue. Everything else is outlined or an icon. That single rule gave the three screens the same hierarchy without extra styling.

(04) Prototyping & iteration

Three passes, each one reviewed with the analyst

Iteration 1: map

Annotate the old screens, agree what stays, what is optional and which eUI component replaces each part.

Iteration 2: rebuild

Recreate the three screens in eUI with the same data and the same labels, so the review could focus on structure.

Iteration 3: refine

Add the controls that the new layout made possible and tidy details found while walking the analyst through the rebuild.

(05) Outcomes & lessons learned

What the redesign delivers

  1. (01)
    One product, not three screens. Header, tabs, buttons and tables now behave the same everywhere, because they come from the same system.
  2. (02)
    Actions you can read. Run actions, file actions and search are separated by intent and labeled where it matters.
  3. (03)
    Data that is easier to scan. Sortable, striped tables and a column picker keep the sparse observation fields out of the way.
  4. (04)
    Less custom work for developers. Each part is a named eUI component, agreed up front.

What I'd do differently

  1. (A)
    Test with statisticians earlier. Walkthroughs with the analyst caught a lot, but the daily users hold the habits no document describes.
  2. (B)
    Annotate in the design tool from day one. Annotated screenshots worked as a brief, but a single living file would have kept the notes and the final screens together.
  3. (C)
    Give the widest tables their own pass. Results can grow to many columns; saved column sets per user would be the next step.
